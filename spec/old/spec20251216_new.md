# tfplan-viewer 新仕様提案 (2025-12-16)

## 設計思想

**ブラックボックスの適切な粒度**:
- 各モジュールは単一責任を持つ
- 1モジュール = 200-300行を目安
- 機能追加時に変更するファイルが明確

## システム構成

```
plan.json + schema.json
    ↓
[1] data_extraction.py (変更なし)
    ↓
Pythonリスト (OriginValueオブジェクト含む)
    ├─ extracted.json (JSON: 可読性用、出力専用)
    └─ extracted.pkl (Pickle: テスト用オプション)
    ↓
[2-1] special_processor.py (新設) ← SPECIAL_RESOURCE_TYPES設定
    ↓
Pythonリスト (特殊処理済み、OriginValueオブジェクト含む)
    ├─ special_processed.json (JSON: 可読性用、出力専用)
    └─ special_processed.pkl (Pickle: テスト用オプション)
    ↓
[2-2] reference_resolver.py (新設)
    ↓
Pythonリスト (参照解決済み、OriginValueオブジェクト含む)
    ├─ resolved.json (JSON: 可読性用、出力専用)
    └─ resolved.pkl (Pickle: テスト用オプション)
    ↓
[2-3] view_converter.py (新設)
    ↓
Pythonリスト (ViewValueオブジェクト含む)
    ├─ formatted.json (JSON: 可読性用、出力専用)
    └─ formatted.pkl (Pickle: テスト用オプション)
    ↓
[3-1] table_generator.py (新設) ← RESOURCE_CONFIGS設定
[3-2] file_organizer.py (新設)  ← RESOURCE_CONFIGS設定
    ↓
HTML出力
```

## 詳細仕様

### [1] data_extraction.py (変更なし)

**責任**:
- schema.jsonからnon-computed属性を抽出（computed専用属性を除外）
- plan.jsonから実際の値を取得
- 参照情報（references）の抽出と保存
- モジュール変数の解決（var.xxx → 実際の参照先）
- ネスト構造の保持（dict/listの再帰処理）
- OriginValueオブジェクトの生成

**入力**:
- `plan.json` (dict): Terraform plan
- `schema.json` (dict): Provider schema

**出力**: Pythonリスト（OriginValueオブジェクトを含む辞書）
```python
[{
  "module": str,           # モジュール名（ルートの場合はNone）
  "address": str,          # リソースの完全アドレス
  "type": str,             # aws_iam_role等
  "name": str,             # リソース名
  "values": dict           # OriginValueオブジェクト（ネスト可能）
}]
```

**主要機能**:
- `_get_non_computed_attributes()`: schema.jsonから非computed属性を抽出
- `_extract_resource_address()`: 参照からリソースアドレスを抽出
- `_build_module_variable_map()`: モジュール変数のマッピング構築
- `_process_value()`: 値の再帰的処理（ネスト構造対応）

### [2-1] special_processor.py (新設)

**責任**: 従属リソースの統合処理のみ

**入力**: Pythonリスト（OriginValueオブジェクトを含む辞書）

**出力**: Pythonリスト（特殊処理済み、OriginValueオブジェクトを含む辞書）
```python
[{
  "module": str,
  "address": str,
  "type": str,
  "name": str,
  "values": dict  # OriginValue（従属リソースが統合済み）
}]
```

**処理内容**:
- 従属リソース（例: `aws_iam_role_policy_attachment`）を親リソースに統合
- 親リソースを指すパラメータ以外の全属性を辞書型で統合
- 統合後、従属リソース自体は削除

**主要機能**:
```python
def process_special_resources(extracted_data: list, special_configs: list) -> list:
    """設定に基づき特殊リソースを処理"""
    # 1. 特殊リソースと通常リソースを分離
    # 2. 各特殊リソースを親リソースに統合
    # 3. 通常リソースのみを返す

def merge_dependent_resource(dependent: dict, parent: dict, config: dict):
    """従属リソースを親リソースに統合"""
    # 親リソースを指すパラメータ（例: role）以外を辞書として追加
```

**設定例** (`SPECIAL_RESOURCE_TYPES`):
```python
[{
  "type": "aws_iam_role_policy_attachment",
  "merge_into": {
    "parent_type": "aws_iam_role",        # 親リソースタイプ
    "parent_key": "attached_policies",    # 親リソースの統合先属性名（配列）
    "match_by": "role",                   # 親リソースとのマッチング属性
    "exclude_keys": ["role"]              # 統合時に除外する属性
  }
}]
```

**入力**:
- デフォルト設定（モジュール内の`SPECIAL_RESOURCE_TYPES`）
- 外部設定ファイル（JSON形式、オプション）

**拡張ポイント**:
- 新しい従属リソースタイプの追加（設定のみ）

## 設定ファイル: special_config.py (新設)

**責任**: 従属リソースの統合設定のみ

### 入力

- **デフォルト設定**: モジュール内の`SPECIAL_RESOURCE_TYPES`（Pythonリスト）
- **外部設定ファイル** (オプション): JSON形式の特殊リソース設定

### 出力

- 各特殊リソースタイプの統合設定
  - 親リソースタイプ
  - 統合先属性名
  - マッチング条件
  - 除外属性

### 設定項目の詳細

```python
SPECIAL_RESOURCE_TYPES = [
  {
    "type": "aws_iam_role_policy_attachment",  # 特殊リソースタイプ
    "merge_into": {
      "parent_type": "aws_iam_role",           # 親リソースタイプ
      "parent_key": "attached_policies",       # 親の統合先属性名（配列）
      "match_by": "role",                      # 親とのマッチング属性
      "exclude_keys": ["role"]                 # 統合時に除外する属性
    }
  }
]
```

### 統合ロジック

1. **マッチング**: 従属リソースの`match_by`属性から親リソースを特定
2. **除外**: `exclude_keys`に指定された属性を除外
3. **統合**: 残りの全属性を辞書型で`parent_key`配列に追加

### 統合例

**従属リソース** (`aws_iam_role_policy_attachment`):
```python
{
  "role": "aws_iam_role.lambda_role",  # マッチング属性（除外される）
  "policy_arn": "arn:aws:iam::...",    # 統合される
}
```

**親リソース** (`aws_iam_role.lambda_role`) の変換:
```python
# 統合前
{
  "name": "lambda-role",
  ...
}

# 統合後
{
  "name": "lambda-role",
  "attached_policies": [               # 新しい配列要素
    {
      "policy_arn": "arn:aws:iam::..."
    }
  ]
}
```

### 外部設定ファイル形式（JSON）

入力形式: JSON配列
```json
[
  {
    "type": "aws_iam_role_policy_attachment",
    "merge_into": {
      "parent_type": "aws_iam_role",
      "parent_key": "attached_policies",
      "match_by": "role",
      "exclude_keys": ["role"]
    }
  }
]
```

### 使用箇所

- **`special_processor.py`**: 設定に基づく自動統合処理

## 設定ファイル: resource_config.py

**責任**: リソースタイプ別の設定のみ

### 入力

- **デフォルト設定**: モジュール内の`RESOURCE_CONFIGS`（Pythonリスト）
- **外部設定ファイル** (オプション): JSON形式のリソース設定

### 出力

- 各リソースタイプの設定情報
  - ファイル配置パス
  - ソート順
  - 優先度
  - 特殊パラメータ設定
  - 列幅設定

### 設定項目の詳細

```python
{
  "resource_types": ["aws_iam_role"],      # 対象リソースタイプ（複数可）
  "file_path": "aws/iam/role.html",        # 出力先HTMLファイル
  "priority": 1,                           # 表示優先度（小さいほど優先）
  "sort_by": "name",                       # ソートキー（"name" | "tags.Name"等）
  "special_parameters": [                  # 特殊表示設定（オプション）
    {
      "name": "assume_role_policy",        # パラメータ名
      "display": "collapsible",            # 表示方法: "collapsible" | "hidden"
      "format_json": true                  # JSON整形（collapsible時のみ）
    }
  ],
  "column_widths": {                       # 列幅設定（オプション）
    "assume_role_policy": "200px",
    "description": "250px"
  }
}
```

### special_parametersの仕様

#### display

- **`"collapsible"`**: クリックで展開可能な折りたたみ表示
  - `<details>`タグで実装
  - `format_json: true`でJSON整形
  - 例: `assume_role_policy`, `policy`, `user_data`

- **`"hidden"`** (将来実装): パラメータを非表示
  - HTMLテーブルに含めない
  - 例: 内部ID等

#### format_json

- **`true`**: JSON文字列をパース＆整形
- **`false`**: 生テキスト表示

### 外部設定ファイル形式（JSON）

入力形式: JSON配列
```json
[
  {
    "resource_types": ["aws_iam_role"],
    "file_path": "aws/iam/role.html",
    "priority": 1,
    "sort_by": "name",
    "special_parameters": [...],
    "column_widths": {...}
  }
]
```

### 使用箇所

- **`resource_processor.py`**: 特殊パラメータ設定（将来）
- **`table_generator.py`**: テーブル形式、列幅、collapsible表示
- **`file_organizer.py`**: ファイル配置、ソート順、優先度

## メリット

### 1. 責任範囲の明確化

各モジュールが単一責任:
- 参照解決は`reference_resolver.py`
- 特殊処理は`resource_processor.py`
- テーブル生成は`table_generator.py`
- ファイル配置は`file_organizer.py`

### 2. ブラックボックスの適切な粒度

- 最大300行程度のモジュール
- 機能追加時に変更するファイルが1つに絞られる
- テストが書きやすい

### 3. 拡張性の向上

**新しい従属リソースタイプの追加**:
- `special_config.py`の設定追加のみ（コード変更不要）

**新しい参照パターンの追加**:
- `reference_resolver.py`のみ変更（150行程度）

**新しいテーブル形式の追加**:
- `table_generator.py`のみ変更（300行程度）

**新しいファイル配置ルール**:
- `file_organizer.py`のみ変更（150行程度）

### 4. 設定駆動の利点

**特殊処理が宣言的**:
- 処理ロジックはspecial_processor.pyに集約
- 新しいパターンは設定追加のみ
- 統合ロジックは共通化（DRY原則）

**入出力が明確**:
- 各モジュールの入出力データ形式が明示的
- Phase間のデータフローが追跡可能
- テストが容易
